# 室内转向、自动打包与马厩侧面显露

整理日期：2026-09-10。依据本轮对话记录；这是设计讨论和下一步工作说明，不是已实现功能。保存本讨论不代表用户已经确认所有助手建议。

## 用户提出了什么

用户明确说明，“内部摆放”不只指马厩中的马、水桶和草槽，也包括其他建筑的独立室内：外部入口转向后，进入房间的方向是否也应对应。用户仍不确定最终取舍，不能再把这一关切写成助手自行推断，也不能据此宣布所有室内都必须旋转。

用户提出考虑房间有没有东西、是否原本为空，并给出两种思路：提供一个开关，或者要求调整时先清空室内。为省去逐个收取的操作，可以自动提供几个大箱子，把室内物品收进去。开关究竟控制什么、清空是否强制、赠送箱子的数量和规则，尚未定案。

用户另提出：保留马厩，当玩家走到建筑外部附近几格时，让马厩侧面变透明，以便看清里面有没有马。这是本轮新增的马厩专用视觉方案，应进入下一次示意验证；不能继续用旧的“只有背面 Reveal”条款排除这一提议。

## 助手建议的室内流程（待选择）

建议将开关定义为“室内跟随建筑转向”，将占用检查与开关配合使用。判断当前房间的实际状态即可；是否从建成起一直为空，不必成为限制。用户尚未选择该组合方案，也未决定开关默认值、全局或单栋范围。

| 场景 | 建议行为 | 需要明确的边界 |
| --- | --- | --- |
| 室内同步关闭 | 外部旋转，室内保持当前布局 | 不因房间有摆放而要求清空；不静默恢复成另一个室内朝向 |
| 室内同步开启，当前没有玩家摆放物 | 检查受支持的室内模板后调整房间和入口 | 固定设施、门、碰撞仍需适配；“没有摆放物”不等于已经检查房间内的角色和动物 |
| 室内同步开启，当前有摆放物 | 提供“打包后调整室内”的候选流程，也可放弃本次室内调整 | 打包不等于自动重新摆好；不应在切换开关时悄悄清空房间 |

另一条仍可研究的路线是保留原物件及状态、将布局整体转向。整体旋转可以保持门、箱子和过道的相对关系，变化主要包括屏幕方向与玩家熟悉的按键路线；不能直接断言它必然打乱摆放。能否处理每种物件仍需分别验证。

“仅允许空房间调整”可以作为室内功能初期的实现范围，但不是已经决定的永久规则，也不扩大首份空牛棚测试包的范围。

## 自动打包需要保留什么

自动装箱解决逐个收取的负担，但玩家之后仍可能要重摆房间。不要把“物品都还在”和“原摆放完整保留”混为一谈。

建议先清点完整物品及所需容器空间，确认箱子在调整后仍有可达、不堵入口的位置，再显示打包结果预览供玩家决定是否执行。箱数按实际需要计算；是否赠送普通大箱子或采用其他收纳形式仍待决定，不新增已确认的经济规则。

检查范围包括家具及其承载物、原箱子的内容和相关属性、机器的待收产物及加工状态、带作物的容器等已支持对象。人物和动物不能作为物品收箱；建筑固定设施需随室内模板另行处理，不能当作杂物删除。

对不能完整保留状态的机器或其他 mod 物件，建议在任何移动发生前指出具体对象并停止本次室内调整。转移应保证失败不会留下丢失、重复或只搬一半的物品。上述保护尚未实现；不能先拆除对象，再尝试寻找可存放位置。

参考版本的 [Let's Move It 移动物件实现](https://github.com/Exblosis/StardewValleyMods/blob/a33106cb20df864685cff8675f21282bde24de37/LetsMoveIt/TargetData/Move.cs) 有沿用原对象并改变其所在集合／位置的路径，说明手动拿起箱子的限制不等于 mod 必须先将所有内容取出。该代码不是本项目的完整保存、回滚或室内旋转方案，不能直接视为兼容证明。[机器数据文档](https://stardewvalleywiki.com/Modding:Machines) 则分别描述产出、加工时间和触发规则，自动打包不能只保留一个空机器物品。此轮未复制上游代码。

## 马厩侧面显露方案

用户目标是在靠近马厩时看清里面有没有马。建议为左／右朝向设置建筑外部、入口及可接近侧边附近的触发区，不预先锁死格数；先在示意中标清范围，再用游戏体验调整。

建议只淡化挡住内部的近侧墙、栏杆与必要屋檐，地基、立柱和轮廓仍可辨认，马与地面保持正常显示；离开后逐渐恢复。每侧一根横栏和用户选定的宽度继续保留。具体淡化哪些结构、各层透明度和过渡速度尚未定稿。

有马与无马都应显示靠近后的内部状态，以满足“确认马在不在”的目标；触发不应依赖马是否存在。这是助手为用户目标补充的实现建议，尚未经实机验证。

透明只改变显示。真实开口、碰撞、停放点、骑乘交互及骑出路径需要另行对齐，不因为画面可见就假定能穿过栏杆或隔墙上马。日常行走也需要触发，不能限定在建筑移动模式。

普通建筑继续沿用原背面 Reveal 方案；马厩侧面作为本轮明确提出的特例进行探索，不能直接把此例外推广到所有建筑。水草无限量仍未采纳；实际养护交互来自哪个 mod、如何保留其收益和数据仍需核对，不能假定用户已安装 Horse Overhaul。

## 接下来按什么顺序做

1. **先做马厩带马的四向使用示意。** 使用 Stable v4 的结构，保留选定宽度和单横栏。统一马与建筑的比例，标出暂定停放位置、玩家接近处和骑出通路；左／右侧分别比较“远处正常”和“靠近显露”，再补充无马状态。站位、触发区属于方案，不能冒充已从游戏验证的坐标。示意验收看遮挡、可辨认性和预留通路；真正的点击、碰撞和骑乘必须留待实机。
2. **再用同一间 Shed 做室内对照。** 使用相同的门、箱子、酒桶和过道布局，比较“只转外部”和“内外整体转向”，看内外进入方向与使用路线的区别；空房／有物品时的开关和打包流程另列示意。此次比较不改用户存档，不直接承诺全部建筑的室内适配。
3. **继续准备首个空牛棚游戏接入。** 核对游戏、SMAPI 和目标搬动 mod 的准确版本及程序集后，依次接移动模式、四向放置／取消、碰撞、人物进出门和存读档。先允许占位图，不要求完成所有马厩或室内方案才能开始。没有这些依赖时，推进接口准备和使用示意，明确未编译／未实机验证的部分。
4. **按示意反馈收敛规则，再逐项扩展。** 室内开关及打包是否采用、作用范围与默认值，以及马厩淡化细节仍需结合可见方案决定。动物、NPC、升级和联机保持后续范围。
